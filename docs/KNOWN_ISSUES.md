# Web (Browser Session) Provider — Known Issues

> **Status**: GLM chat works end-to-end (login → chat → stream response). 2 known UX issues remain from 2026-06-05 manual E2E.

## Issue 1: Stop button is not fully effective (DOM-injection path)

**Symptom**: Clicking the red "Stop" button in the chat sidepanel stops the stream UI immediately. Clicking it a second time does nothing. After ~5-30 seconds, the reply text continues to populate in the assistant message bubble (with the "cancelled" indicator).

**Root cause**: The chat-injection adapter (GLM) runs inside a `chrome.scripting.executeScript({world: 'MAIN'})` call in the chatglm.cn tab. `chrome.scripting` has **no abort signal**: once the IIFE starts polling the DOM (every 100ms), it cannot be cancelled from the SW. The full sequence:

1. User clicks Stop → `useBackgroundAgent.cancel()` → SW receives cancel message
2. SW sets `terminated = true` in `orchestrateStream` and calls `stream.end()` ✓
3. The MAIN-world IIFE is still running its polling loop, reading the AI reply from the DOM
4. The reply is still being generated by chatglm.cn (the user pressed Stop in our sidepanel, not in the provider's tab)
5. When the IIFE detects the reply is "stable" (text unchanged for `stableThresholdMs = 800ms`), it pushes `WEB_LLM_DONE` to the ISOLATED bridge
6. Bridge forwards to SW
7. SW receives DONE; the `terminated` check at the top of the message handler SHOULD return early, but `accumulatedText` has been built up during the post-stop period
8. The chat side displays the residual text in the assistant message

**Why we won't fix this in MVP**: Adding an abort channel requires:
- Inject a `chrome.runtime.connect` port (bidirectional) into the content script
- Content script must `await`-poll this port for an abort message between each DOM read
- Survives across the IIFE serialization boundary (functions in MAIN world can't access ISOLATED-world port objects)

This is ~1-2 hours of careful work touching both the bridge injection (`installIsolatedBridge`) and the polling loop (`runDomRelayMainWorld`). Defer to a follow-up.

**Workaround for users**: Don't rely on the Stop button to immediately kill the stream. The stream eventually stops (when the AI finishes or times out via the `WEB_SESSION_TIMEOUT_MS` watchdog). If you need a hard stop, close the chatglm.cn tab — the next attempt will show a "session expired" toast.

## Issue 2: 401 detection missing on the DOM-injection path (browser-side logout silently ignored)

**Symptom**: User logs out of chatglm.cn in their browser (clears cookies, or clicks "Sign out" on chatglm.cn directly). Cebian sidepanel can still successfully send a message via the Web (Browser Session) model and get a response.

**Root cause**: The ⑨.x 401 detection (`WEB_LLM_NEEDS_RELOGIN` flow in `web-provider-relay.ts` + `web-provider-relogin.ts`) is wired only into `executeChatRequest()`, the **HTTP-replay path** used by Kimi (now removed) and DeepSeek (now removed). It is **NOT wired into the DOM-injection path** used by GLM.

The DOM-injection path works like this:
- SW opens a tab at `https://chatglm.cn` (the user's already-logged-in browser session)
- Injects a content script that reads the AI reply from the page's DOM
- The SW does NOT make a network request → no HTTP status code is ever seen
- If the user logs out in the browser, the page is now on a login wall, but the SW doesn't know

There IS a partial mitigation: the content script's pre-flight check (in `runDomRelayMainWorld`) verifies that the chat input element is present on the page. If the user landed on a login wall, the input is gone, and the script emits `WEB_LLM_NEEDS_RELOGIN`. BUT this only works if:
- The user is on the chat page when they send the message
- The page has fully loaded the login wall (not stuck in a redirect)

In practice, if the user logs out in another tab and the SW's reused tab still has the chat page loaded, the input element is still there → DOM injection proceeds normally → "successful" chat with the now-invalid session.

**Fix (2026-06-07, commits `e721fcf` + `6b6dabc`)**: A new BG-resident **session watcher** now runs on every SW boot. For each preset whose Dexie `loginStatus === 'loggedIn'`, it:
1. Subscribes to `chrome.cookies.onChanged` for the preset's `cookieDomain` (debounced 500ms; leading-dot domain shape tolerated)
2. Runs a periodic 5-min probe that re-reads the session-indicator cookies
3. On either trigger, runs the same `WEB_LLM_NEEDS_RELOGIN` flow that the HTTP-replay 401 path already produces — invalidates the bundle cache and broadcasts to the sidepanel

**Module-level pieces**:
- `lib/ai-config/web-provider-session-watcher.ts` — pure predicates (`detectSessionLost`, `shouldFireOnCookieChange`) + dep-injected `startSessionWatcher` lifecycle
- `entrypoints/background/web-provider-session-watcher-bg.ts` — BG wiring (`installSessionWatcher`); reads Dexie, dispatches cookie changes, handles `relogin_success` (restarts the watcher for that provider)
- `entrypoints/background/index.ts` — invokes `installSessionWatcher()` once on SW boot, alongside the existing `registerWebProviderReloginHandler`
- `lib/ai-config/web-provider-cookie-service.ts` — exports the new `listCookiesForDomain` helper

**Tests**: 18 session-watcher + 10 BG-wiring = 28 new tests, full vitest 288/288. `pnpm check` 0 new errors (61 baseline = 61 current). Build 9.62 MB / 0 high-risk.

## Already fixed (2026-06-05)

### ✅ Issue 3: "No model selected" after logout from settings
**Was**: Logout from Settings → next chat → "No model selected or model not found" (confusing; user expects a "please re-login" message).

**Fix**: `lib/ai-config/web-provider-active-model.ts` + `WebProvidersSubSection.tsx:onLogout`. On logout, if `activeModel` points at `web:<loggedOutId>:*`, clear it. Sidepanel naturally shows the "please select a model" prompt.

**Test**: `__tests__/lib/ai-config/web-provider-active-model.test.ts` (6 cases, including the `glm` vs `glm-2` colon-boundary edge case).
