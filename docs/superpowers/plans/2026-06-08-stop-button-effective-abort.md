# Plan: Issue 1 — Stop button not fully effective (DOM-injection path)

> **For agentic workers:** Pick this up when the user is ready. Stop button is a real UX issue — clicking it should actually stop the AI reply mid-stream.

## Goal
Make the red "Stop" button in the chat sidepanel **actually cancel** the in-flight AI reply, so no residual text appears in the assistant message bubble after Stop is clicked.

## Root cause (from `docs/KNOWN_ISSUES.md`)

The chat-injection adapter (GLM) runs inside a `chrome.scripting.executeScript({world: 'MAIN'})` call in the chatglm.cn tab. `chrome.scripting` has **no abort signal**: once the IIFE starts polling the DOM (every 100ms), it cannot be cancelled from the SW. The full sequence:
1. User clicks Stop → `useBackgroundAgent.cancel()` → SW receives cancel message
2. SW sets `terminated = true` in `orchestrateStream` and calls `stream.end()` ✓
3. The MAIN-world IIFE is still running its polling loop, reading the AI reply from the DOM
4. The reply is still being generated by chatglm.cn
5. When the IIFE detects the reply is "stable", it pushes `WEB_LLM_DONE` to the ISOLATED bridge
6. Bridge forwards to SW; SW's `terminated` check returns early, but `accumulatedText` has been built up

## Proposed approach (Option A — port-based abort)

Add a **bidirectional abort channel** between the SW and the MAIN-world IIFE via `chrome.runtime.connect`:

1. **SW side** (`lib/ai-config/web-provider-stream.ts:orchestrateStream`):
   - When starting a chat, open `chrome.runtime.connect({name: `abort-${sessionId}`})`
   - Keep the port reference in the session state
   - On `cancel(sessionId)`, call `port.postMessage({type: 'abort'})` then `port.disconnect()`

2. **Content-script bridge side** (`lib/ai-config/web-provider-content-script.ts`):
   - The ISOLATED bridge listens for `abort` messages from the port
   - Forwards abort to the MAIN world via `window.postMessage({type: 'WEB_LLM_ABORT'})`

3. **MAIN-world IIFE** (`web-provider-content-fetch-glm.ts` `runDomRelayMainWorld`):
   - At the top of the polling loop, check `window.__webProviderAbortFlag`
   - If set, break the loop and post `WEB_LLM_DONE` (so SW cleans up)

The flag is set by a separate `window.addEventListener('message', ...)` handler that listens for `WEB_LLM_ABORT` from the ISOLATED bridge.

## Architecture diagram
```
SW: cancel(sessionId)
  ↓ port.postMessage({type:'abort'})
ISOLATED bridge: port message → window.postMessage({type:'WEB_LLM_ABORT'})
  ↓
MAIN world: window message handler sets window.__webProviderAbortFlag = true
  ↓
MAIN world: polling loop checks flag, breaks early
  ↓
ISOLATED bridge: receives WEB_LLM_DONE (with truncated text), forwards to SW
  ↓
SW: terminated check returns early, cleans up
```

## Key files to touch

| File | Change |
|---|---|
| `lib/ai-config/web-provider-stream.ts` | Open abort port on chat start; close on cancel |
| `lib/ai-config/web-provider-content-script.ts` | Listen on abort port; forward to MAIN world via window.postMessage |
| `lib/ai-config/web-provider-content-fetch-glm.ts` | Add `__webProviderAbortFlag` window global; check in polling loop |
| `entrypoints/background/index.ts` | Manage port lifecycle per session (open on prompt, close on done/error/cancel) |

## Risks

| Risk | Mitigation |
|---|---|
| Port cleanup leaks memory on session destroy | Disconnect port in `finally` of `orchestrateStream` |
| IIFE misses the abort if it's mid-await | Re-check flag at start of each iteration of the polling loop |
| Multiple sessions in flight → ports collide | Use unique port name `abort-${sessionId}` |
