## 1. LLM 输出质量判断（18 个）

### 涉及用例

| 用例ID | 场景 | 自动化难点 |
|--------|------|-----------|
| TC-1.2.1 | 纯文本消息响应 | 无法断言 LLM 输出内容是否正确 |
| TC-2.1.1 | 阅读页面总结 | 无法断言总结是否准确、要点是否完整 |
| TC-2.1.2 | SPA 页面阅读 | 动态内容判断需要语义理解 |
| TC-2.1.3 | 登录后页面阅读 | 涉及权限内容，无法 mock |
| TC-2.2.1 | 截图分析图表 | 无法断言 AI 是否正确识别图表内容 |
| TC-2.2.2 | 复杂 UI 截图分析 | 视觉理解无法程序化验证 |
| TC-2.3.1~2.3.8 | 操作页面系列 | LLM 决策过程不可预测，无法断言操作序列 |
| TC-2.4.1~2.4.2 | 填写表单 | 无法断言 AI 是否正确理解表单意图 |
| TC-4.4.1 | 录制回放登录流程 | 真实登录涉及验证码等不可自动化因素 |
| TC-6.2.1 | MCP 工具调用结果 | 真实工具执行结果不可预测 |

### 替代方案：结构化断言 + MiniMax M3 确定性 Prompt

```typescript
// 在 E2E 中使用确定性 prompt，对响应做结构化断言
const prompt = 'Reply with the single word: PONG';
await sendChatMessage(sp, prompt);
const reply = await waitForAssistantResponse(sp);
// 不判断内容质量，只判断响应存在且非空
expect(reply.length).toBeGreaterThan(0);
```

**推荐实践**：
1. 对 LLM 输出不做内容正确性断言，只断言**响应存在、格式正确、无错误**
2. 使用确定性 prompt（如"只回复一个词：PONG"）来验证端到端链路通畅
3. 内容质量通过**定期人工抽检**（每周抽检 10% 用例）来保障

## 2. 视觉/截图验证（12 个）

### 涉及用例

| 用例ID | 场景 | 自动化难点 |
|--------|------|-----------|
| TC-1.3.1 | 代码块语法高亮 | 颜色、字体需要视觉确认 |
| TC-1.3.2 | 表格渲染对齐 | 像素级对齐难以程序化判断 |
| TC-1.3.5 | 图片加载 | 需要确认图片真实渲染 |
| TC-1.3.6 | 文本两端对齐 | 需要人眼确认边缘整齐 |
| TC-1.4.1 | 图片附件上传预览 | 缩略图渲染需视觉确认 |
| TC-2.2.1~2.2.5 | 截图分析系列 | AI 视觉理解结果无法程序化验证 |
| TC-4.3.7 | 排序后 key 稳定 | 虽然已自动化，但复杂排序场景需人工确认 |
| TC-5.3.2 | 截图留痕 | 截图内容正确性需人工确认 |

### 替代方案：Playwright 截图对比 + 人工审核

```typescript
// 对关键视觉状态截图，存入 baseline
await expect(page).toHaveScreenshot('code-block-render.png', {
  maxDiffPixels: 100,
});
```

**推荐实践**：
1. 使用 Playwright `toHaveScreenshot` 做视觉回归测试
2. 首次运行生成 baseline，后续对比差异
3. 差异超过阈值时人工审核
4. 关键页面（聊天界面、设置页）纳入视觉回归套件

| TC-6.2.1~6.2.4 | MCP 调用系列 | 需要真实服务响应 |

| TC-8.1.3 | 登录态过期 | 需要等待真实过期时间 |

### 替代方案：Mock + 契约测试 +  staging 环境人工验证

```typescript
// E2E 中使用 Mock（已实现）
await page.route('http://127.0.0.1:8080/**', async (route) => {
  await route.fulfill({ body: JSON.stringify({ success: true }) });
});
```

**推荐实践**：
1. **E2E 自动化层**：全部使用 Mock，验证 UI 流程和调用契约正确
2. **契约测试层**：验证 Mock 响应与真实 API schema 一致（定期同步）
3. **Staging 人工层**：在真实 BrowserWing/MCP 环境下，由测试人员执行关键路径验证

## 4. 浏览器/环境特殊场景（8 个）

### 涉及用例

| 用例ID | 场景 | 自动化难点 |
|--------|------|-----------|
| TC-10.1.2 | SW 崩溃重启 | 强制终止 SW 在 Playwright 中难以稳定复现 |
| TC-10.2.2 | IndexedDB 迁移 | 需要跨版本扩展，环境搭建复杂 |
| TC-10.2.3 | 存储配额满 | 模拟存储满需要特殊浏览器配置 |
| TC-10.3.1 | Chrome 兼容性 | 已默认在 Chrome 运行，但深度兼容需人工 |
| TC-10.3.2 | Firefox 兼容性 | Playwright 配置为 Chrome 项目，需额外配置 |
| TC-10.3.3 | 不同分辨率 | Playwright 可改 viewport，但真实设备适配需人工 |
| TC-1.2.6 | 网络中断 | 模拟断网在 headed 模式下不稳定 |
| TC-2.5.3 | 忽略 loading spinner | 需要精确控制页面加载时序 |

### 替代方案：分层环境验证

| 环境 | 验证方式 | 频率 |
|------|---------|------|
| 开发环境 | Playwright E2E（Mock + 理想条件） | 每次提交 |
| CI 环境 | Playwright E2E（headless，如支持） | 每次 PR |
| Staging | 真实浏览器 + 真实网络 + 人工验证 | 每周 |
| 预发布 | 全浏览器矩阵（Chrome/Firefox/Edge） | 每次发布前 |

## 5. 复杂交互时序（5 个）

### 涉及用例

| 用例ID | 场景 | 自动化难点 |
|--------|------|-----------|
| TC-2.5.7 | 冷却期机制 | 8000ms 防抖 + 30000ms 冷却，测试耗时且不稳定 |
| TC-3.1.5 | 低于阈值不触发 | 精确控制 DOM 变化数量困难 |
| TC-4.2.3 | cap-trigger 自动停止 | 需要构造大量事件或长时间等待 |
| TC-4.4.5 | 超时处理 | 需要精确控制元素出现时机 |
| TC-6.2.2 | 限流保护 | 快速连续请求在单 worker 下难以模拟 |

### 替代方案：单元测试覆盖 + E2E 简化验证

```typescript
// 在 Vitest 中对时序逻辑做单元测试
it('cooldown prevents duplicate notifications', async () => {
  // 直接测试 page-watcher.ts 的纯逻辑，无需浏览器
});
```

**推荐实践**：
1. 时序敏感逻辑在 **Vitest 单元测试** 中验证（已覆盖 `page-watcher.test.ts`）
2. E2E 中只做**简化验证**（如验证按钮可点击，不验证精确时序）
3. 关键时序通过**代码 review + 静态分析**保障

## 建议的测试金字塔

```
        /\
       /  \  人工测试 (15%)
      / 視 \  视觉回归 + Staging 验证
     / 覺  \  
    /________\  E2E 自动化 (35%)
   /          \  Playwright + Mock
  /____________\  单元测试 (50%)
 /              \  Vitest + jsdom
/________________\
```

| 层级 | 比例 | 工具 | 覆盖范围 |
|------|------|------|---------|
| 单元测试 | 50% | Vitest | 纯逻辑、状态管理、工具函数 |
| E2E 自动化 | 35% | Playwright | UI 流程、交互链路、Mock 外部服务 |
| 人工/视觉 | 15% | 人眼 + 截图对比 | 内容质量、视觉渲染、真实服务验证 |

## 执行建议

1. **每次提交**：运行 `pnpm test`（Vitest 739 个单元测试）+ `pnpm test:auto`（80 个 E2E 自动化用例）
